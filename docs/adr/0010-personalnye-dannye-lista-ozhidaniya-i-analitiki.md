# 0010. Персональные данные листа ожидания и аналитики лендинга

## Контекст

Публичный сайт собирает лист ожидания и считает воронку «просмотр → расчёт нормы → запись → регистрация → первая покупка» по источникам (QR в зале, тренер, Telegram, Instagram). Бриф требовал аналитику без сторонних трекеров и без cookies и просил согласовать, что считается персональными данными и что требует согласия. Владелец выбрал «больше аналитики»: постоянный анонимный номер браузера, чтобы видеть путь одного человека от просмотра до покупки. Здесь записано техническое решение; юридическую оценку и формулировки даёт юрист (см. «Не решено»).

## Решение

**Что считаем персональными данными.** Телефон, имя, зал или район и цель из листа ожидания. Анонимный номер браузера (`anonId`) тоже: его не показывают людям, но он связывает записи одного человека, а в листе ожидания лежит рядом с телефоном.

**Что персональными данными не считаем.** Безымянные счётчики по источнику: событие `landing_view` или `calc_used` без `anonId` содержит только вид события, источник, метки `ref` и `campaign` и время. Адрес клиента (IP) нигде не сохраняется: он нужен только для лимитов запросов в памяти процесса.

**Что требует согласия.**

- Запись в лист ожидания: отмеченная галочка в форме, не отмеченная заранее. Сервер отклоняет запись без `consent: true` (400). Версия текста (`WAITLIST_CONSENT_VERSION`) и момент согласия лежат в самой записи. Согласие считается данным при первой записи; повтор того же номера запись не меняет.
- Постоянный анонимный номер: плашка на лендинге. «Принять» создаёт в `localStorage` ключ `sportpit.aid` (UUID) и ключ `sportpit.analytics`. «Только необходимое» оставляет безымянные счётчики, номера нет. Выбор меняется со страницы `/legal`. Сервер ничего не решает за браузер: `anonId` пишется, только если он пришёл.

**Что не требует отдельного согласия.** Безымянные счётчики без `anonId` и источник регистрации без номера: они не позволяют узнать человека.

**Где что лежит** (миграция `101-growth.sql`, модуль `growth`).

| Таблица | Что хранит | Связь с человеком |
|---|---|---|
| `waitlist_entries` | телефон, имя, зал, цель, язык, источник, версия и время согласия, `anon_id` | по телефону; `anon_id`, если дал аналитику |
| `funnel_events` | вид события, источник, `ref`, `campaign`, `anon_id`, время | только по `anon_id`; к телефону и пользователю не привязана |
| `signup_attribution` | источник новой регистрации, `anon_id`, время | по `user_id` |

В ответах API наружу `anon_id` не отдаётся ни в списке листа ожидания, ни в выгрузке: админ видит только отметки пути («считал норму», «зарегистрировался», «купил»), посчитанные по этому номеру на сервере.

**Чего нет.** Cookies сайта (кроме сессии входа `sp_session` у вошедших), сторонних трекеров, пикселей, внешних шрифтов и CDN, отпечатков браузера, хранения IP, ввода калькулятора (рост, вес, возраст, цель, ограничения): расчёт идёт в браузере, на сервер уходит только факт события `calc_used` без цифр. Номер из листа не используется для рассылки: рассылки в этой сборке нет.

**Права человека.**

- Удаление аккаунта (`POST /profile/account/delete`) стирает строку `signup_attribution` пользователя: хук `growth`. Событие `signup` в `funnel_events` остаётся без привязки к человеку (в нём нет ни пользователя, ни телефона).
- Запись листа ожидания удаляет администратор по просьбе человека (`DELETE /admin/waitlist/:id`); действие записывается в `admin_audit` по номеру записи, без телефона и имени. Удаление аккаунта запись листа по телефону автоматически не стирает: у записи нет связи с пользователем. Это решается просьбой к администратору, пока политика хранения не названа.
- Человек сам убирает анонимный номер, очистив данные сайта в браузере или выбрав «Только необходимое» на `/legal`; серверные записи с ним при этом остаются безымянными по смыслу, но связаны между собой через этот номер.

**Защита.** Лист и воронка видны только роли `admin` (проверка на сервере). Публичные маршруты защищены лимитами в памяти процесса (запись: 30 в час на IP и 3 в сутки на номер, события: 120 в минуту на IP), скрытым полем-приманкой и тем, что ответ на повтор номера не отличается от ответа на новую запись: наличие номера в листе не раскрывается. Выгрузка CSV защищена от формул Excel (телефон выводится с апострофом).

## Почему

Анонимный номер владелец выбрал сам ради пути одного человека; без согласия его нет, поэтому плашка нужна, а сторонние сервисы аналитики не нужны. Хранить IP незачем: лимиты обходятся памятью процесса. Ввод калькулятора не хранится никогда, чтобы не собирать данные о здоровье без согласия `health_data`, которое существует только для вошедших.

Отвергнуто: общий журнал `system_events` для событий воронки (он про сбои, питает алерты и счётчик `/api/health`); хранение согласия на лист в таблице `consents` (там внешний ключ на пользователя и закрытый список видов, а у человека из листа пользователя нет); подтверждение номера кодом для листа (усложняет форму, защита — лимиты и приманка; проверка появится вместе с реальной рассылкой).

## Последствия

- `signup_attribution` и `waitlist_entries` связывают `anon_id` с человеком. Пока срок хранения не назван, данные лежат без ограничения по времени.
- Любое расширение (рассылка людям из листа, новые поля формы, новые события с идентификаторами) требует пересмотра этого решения и поднятия `WAITLIST_CONSENT_VERSION`, если меняется текст согласия.
- Страница `/legal` описывает то же простыми словами; юридические формулировки там заготовки `[ВПИШИ]`.
